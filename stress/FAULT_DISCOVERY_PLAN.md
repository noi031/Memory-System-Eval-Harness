# EchoMem 故障发现型压测补充方案

本方案建立在 PR28 的真实 HTTP、多租户隔离、Commit barrier、429
Retry-After、请求级证据和服务端遥测基础上。目标不是增加更多漂亮的并发数字，
而是回答数据是否正确、异常后是否可恢复、一个租户是否会拖垮其他租户。

## 分级

| 级别 | 范围 | 结论要求 |
| --- | --- | --- |
| S1 | 数据正确性、隔离、幂等、背压 | 任一数据错误直接 FAIL |
| S2 | 优先级、限流、恢复 | 需要请求级服务端证据；缺失则 INCONCLUSIVE |
| S3 | 长稳态、资源回收、冷启动 | 至少重复 3 轮，不能用单次结果下结论 |
| S4 | 故障注入 | 需要可控的依赖、进程或网络故障开关 |

## S1：必须优先补充

### 1. 写后读一致性

流程：

1. 写入唯一 marker。
2. 提交并等待异步状态为 `completed`。
3. 立即检索 marker，持续记录直到命中或超时。

输出：

- `commit_completed_at`
- `first_visible_at`
- `visibility_latency_ms`
- `visibility_timeout`
- `not_visible_after_completed`

判定：

- commit 已完成但最终未检索到 marker：FAIL。
- 可见延迟超过业务阈值：FAIL。
- 没有足够的完成和检索样本：INCONCLUSIVE。

### 2. Commit 幂等性

对同一个 session 使用相同请求标识重复提交，覆盖：

- 第一次提交成功，第二次重复提交。
- 第一次返回超时，客户端重试。
- 收到 `202` 后重复轮询。

输出：

- 提交次数和尝试次数。
- 唯一 archive/operation 数量。
- 重复记忆数量。
- 最终状态是否一致。

判定：

- 同一幂等请求产生多个实际写入：FAIL。
- 服务不支持幂等键时，必须标记 `NOT_IMPLEMENTED`，不能默认为通过。

### 3. Commit 状态机

记录每次状态轮询的完整序列，例如：

```text
accepted -> pending -> processing -> completed
```

禁止出现：

- `completed -> pending`
- `failed -> completed`，除非有明确 retry attempt 标识。
- 已接受任务无 archive/operation ID。
- 超时后任务永远没有最终状态。

### 4. 背压与恢复

逐步提升 Commit 到队列满，再逐步降载，观察：

- 429/503 是否符合服务端容量策略。
- `Retry-After` 是否存在且可执行。
- 队列是否在降载后回落。
- 新请求是否能恢复成功。
- 已接受任务是否最终排空。

判定：

- 无限接受导致队列持续增长：FAIL。
- 返回 429 但无 Retry-After：记录为风险；若业务要求客户端可恢复则 FAIL。
- 降载后队列不回落或成功率不恢复：FAIL。

## S2：性能故障定位

### 5. Search 优先级和连续洪峰

PR28 已有单次 Commit barrier。补充连续 3 至 5 个洪峰，每个洪峰之间设置
固定冷却窗口，分别比较：

- 洪峰前 Search P50/P95/P99。
- 洪峰期间 Search P50/P95/P99。
- 洪峰后的恢复时间。
- Search 超时率和 Commit 队列深度。

只比较成功请求延迟，同时单独报告整体超时率，避免把 10 秒客户端超时直接
混入服务端处理延迟。

### 6. 租户倾斜和抗饥饿

让租户 A 持续制造高流量，B/C/D 保持低流量，记录：

- 每个租户的 Search 成功率和 P95。
- 最大连续未服务时间。
- 每个租户的 Commit 完成率。
- A 的负载对 B/C/D 的 P95 劣化倍数。

判定：

- 低流量租户被高流量租户持续饿死：FAIL。
- 只有一个独立凭证或缺少服务端租户字段：公平性结论为 INCONCLUSIVE。

## S3：稳定性和资源回收

### 7. 取消、断连和超时回收

客户端在 Search 或 Commit 处理中主动断开连接，随后观察：

- inflight 是否回落。
- 线程数和 FD 是否回落。
- commit 队列是否残留不可完成任务。
- 服务端是否出现孤儿任务。

### 8. 冷启动、热启动和重启恢复

分别测试：

- 服务启动后的首个 Search/Commit。
- 预热后的稳定请求。
- 服务重启后的首个请求。
- 重启前已接受 Commit 的最终状态。

### 9. 长时间 soak

至少运行 30 分钟；正式验收建议 2 小时。每 5 分钟生成窗口指标：

- RSS、CPU、线程、FD、Swap。
- Search/Commit 成功率。
- 队列深度和最大等待。
- 后台任务数量。

内存结论必须比较相同冷却状态下的基线和结束值，不能仅凭单次 RSS
斜率判定“无泄漏”。

## S4：故障注入

只有部署环境支持可控故障时才执行：

- 向量库短暂不可用。
- LLM 请求超时或返回 5xx。
- Commit worker 重启。
- 网络延迟、连接重置。
- 服务进程重启。

每次故障都必须验证：

1. 新请求是否按预期失败或退避。
2. 已接受任务是否丢失。
3. 恢复后是否继续处理。
4. 是否产生重复记忆。
5. 报告是否能关联原始 request_id。

不能注入真实故障时统一输出 `NOT_IMPLEMENTED`，不使用 mock 结果替代。

## 统一判定门槛

在 PR28 现有门槛上增加：

```text
跨租户误命中率 > 0                 FAIL
commit completed 后 marker 未可见    FAIL
最终状态未知或 drain 后仍未完成       FAIL / INCONCLUSIVE
重复幂等请求产生重复写入              FAIL
高负载后队列不回落                    FAIL
Search 超时率 > 1%                    FAIL
低流量租户连续未服务超过业务阈值       FAIL
关键服务端遥测缺失                    INCONCLUSIVE
```

## 与当前报告的对应关系

当前报告已经暴露了三类需要用新增特性继续确认的问题：

- `D@4` 的 Search P95 劣化，需要用连续洪峰和成功请求延迟拆分复现。
- 30 个 Commit 在轮询窗口内未完成，需要用最终 drain 和状态机记录区分
  “真正失败”与“观察窗口不足”。
- 并发 16 下错误率很高，需要增加队列背压、取消回收和恢复测试，而不是
  只继续提高并发。
