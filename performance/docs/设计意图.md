# performance 设计意图

通用 HTTP 压测框架：**场景语义是 Python 代码，负载画像是 YAML 数据**。
按被测系统组织（`targets/<system>/`），`targets/echomem/scenes/` 下四个场景
是 legacy 压测体系 A/B/C/D 四场景的无损翻译。

## 1. 目标与定位

对任意 agent/记忆系统的 HTTP 接口（按被测系统组织）做可控、可复现、可对比的负载压测：

- **通用运行时**（worker 池、到达模型、计时、指标、报告）与**具体接口语义**（请求序列、事务、质量断言）解耦，二者都能独立演进；
- 一个引擎运行时服务所有被测系统；新接入一个系统 = 新增 `targets/<system>/` 子包（协议适配 + 场景 + 画像），通用层零改动；
- 记录口径与 legacy 压测体系（loadgen）对齐，两份压测结果可直接对比。

## 2. 为什么场景语义是代码而不是 YAML

上一版把场景语义放进 YAML 数据包（schema/templating/loader），翻译四场景时暴露三处无法无损表达的缺口，每个都要发明新 schema 关键字：

| 场景 | 缺口 | 需要的「关键字」 |
|---|---|---|
| B add×N | 循环内联 | `step.repeat` |
| C 8:1 混合 | 多事务类型 + 权重拆 worker | `load.mix` |
| D 中点洪峰 | 时间触发注入 | `load.burst`（阶段原语） |

且有一类语义在数据里永远表达不了：依赖响应做条件决策（按错误码重开 session、按返回内容分叉）——这是控制流，声明式结构没有执行上下文。行业先例（Locust=Python、k6=JS、Gatling=Scala DSL、JMeter=XML+逻辑控制器）同样把场景语义放代码；legacy 压测体系里每后端一个 Python 客户端子类（`client.py`）也是代码表达接口语义。结论：**凡表达顺序/分支/循环/并发/时间的，是程序，放代码；凡改数值换压法的，是配置，放数据。**

## 3. 四层架构

| 层 | 内容 | 载体 | 文件 |
|---|---|---|---|
| 通用运行时 | worker 池、到达门、阶段注入、记录、统计、报告、CLI | 代码 | `engine.py` `ctx.py` `records.py` `stats.py` `report.py` `run.py` |
| 被测系统 | 协议适配：**端点级函数**（每个 = 一个 HTTP 端点）+ **标准任务**（端点组合成的事务）+ **探针**（单次行为验证） | Python | `targets/<system>/protocol.py` `targets/<system>/probes/` |
| 场景语义 | 任务函数、事务序列、循环/重试/混合/突发、质量断言；import 本系统 protocol 的端点/标准任务 | Python | `targets/<system>/scenes/scene_*.py` |
| 负载画像 | target/headers/workers/duration/mix/arrival/params | YAML | `targets/<system>/profiles/*.yaml` |

`targets/` 是一个个自包含的被测系统子包；通用层不 import 任何 `targets` 模块，引擎通过文件路径加载场景，场景再 import 本系统的 `protocol`。当前实现 `targets/echomem/`（commit/search 端点）。

## 4. 场景文件契约（`targets/<system>/scenes/*.py`）

场景模块必须导出：

- `task(ctx)`：单个任务函数；或
- `tasks`：`{任务名: 函数}` 映射（多任务混合时用）。

可选导出：

- `schedule(ctx)`：在 worker 启动前调用一次，用于注册阶段注入（`ctx.at_time`/`ctx.at_ratio`）；
- `report(result, profile) -> dict`：跑完后返回 JSON-safe 的系统特有分析，合并进 summary 的 `custom` 段（见 §8）。

函数签名统一为 `fn(ctx: Ctx) -> None`，代表**一次**请求/事务；引擎按 worker 循环调用直到 duration 结束。下划线开头的模块是辅助（非场景）。系统级辅助集中在 `targets/<system>/protocol.py`（协议适配），场景从其中 import 端点级函数与标准任务，不在场景文件里重复传输细节。

**边界**：场景文件只描述接口语义，不含负载控制（并发、到达、时长）；引擎对接口一无所知（不 import 具体系统），只扫 `targets/*/scenes` 按文件路径加载场景。

## 5. ctx API 契约（`ctx.py`）

七个原语 + 记录扩展，全部由引擎实现，场景作者不重写传输/计时/分类：

| 原语 | 作用 |
|---|---|
| `ctx.post/get/request(method, path, *, body, params, headers, timeout_s, op, extra, **fields)` | 发请求；自动套 base_url/公共头/超时；**自动记录**；任何传输结果都返回 `Response` 不抛异常 |
| `Response` | `.ok`/`.status`/`.http_status`/`.elapsed_ms`/`.json`/`.body_text`；`.require_status(code)` 不匹配抛 `AssertionFailure` |
| `ctx.poll(path, *, op, interval_s, timeout_s, until, failed_statuses, **fields)` | 轮询状态直至 completed/failed/timeout；记录单条结果（`commit_timeout`/`commit_failed`） |
| `ctx.choose(items)` | 线程安全轮询取数据（替代 `{query}` 模板） |
| `ctx.next_seq()` / `ctx.worker_id` / `ctx.tenant_idx` / `ctx.tenant_count` / `ctx.params` / `ctx.duration_s` / `ctx.base_url` / `ctx.extra` | 运行时身份与画像只读视图 |
| `ctx.at_time(t, fn, *, count, max_workers, name, tenant_idx, tenant_counts)` / `at_ratio(ratio, ...)` | 注册一次性阶段注入；`count` 个 `fn` 以 `max_workers` 并发执行。`tenant_idx` 令全部 job 属同一租户（默认首个）；`tenant_counts={tenant_idx: count}` 把 job 分布到多个租户、在同一并发阶段内一起执行（此时 `count`=映射求和，不可另传） |
| `ctx.note(**fields)` / `ctx.record(...)` | 响应后补字段 / 手动记录 |

**记录语义**：

- HTTP 2xx/3xx → `status=ok`；HTTPError → `status=error` + `error_type=http_4xx/http_5xx`（保留 `http_status`、`reason_code`）；timeout/连接 → `error_type=timeout/connection`；
- 每个请求/poll 恰好一条记录，无吞没；
- `ctx.note` 只更新本 ctx 最近一条记录（响应派生的字段如 `hit_count`/`quality_ok`）。

**传输**：每线程一条 keep-alive HTTP/1.1 连接，按 `base_url` 复用（连接建立开销不进延迟测量，也避免高 churn 耗尽客户端 socket）。发送阶段失败（连接被拒/陈旧）丢弃连接并**重试一次**——此时请求字节尚未发出，重试不会重复写；响应阶段失败不重试（请求可能已送达，重试会重复写事务）。连接登记在**每所有者一个的 `ConnectionRegistry`**（每个 Engine / 探针运行各持一个，无进程级全局强引用集合）：正常收尾在 `run()` 的 finally 中关闭并注销本所有者全部连接（顺序 case 不跨 case 累积客户端描述符）；超时中断（`Engine.stop()`）先置 `interrupt`/`stop` 事件，再有界 shutdown 本注册表连接**与在途响应句柄**的底层 socket——不等缓冲响应读取、不阻塞，Windows/Linux 均打断阻塞 recv，worker 的读返回后（OSError 或 EOF 均检查 interrupt）映射为 `error_type=stopped`。`Connection: close` 响应会让 `http.client` 的 `getresponse` 把 `conn.sock` 摘除（socket 所有权转给响应），因此每个在途响应在 body 读取期间也登记为可取消句柄，停机一并打断其阻塞读。注册表带**关闭代际守卫**：停机（`shutdown_all`）置位后，迟到的连接/响应注册立即被关闭并拒绝（`stopped`），请求方不再进入 I/O——停机与 worker 退出都有界、不依赖服务端结束响应。连接在**登记前先建连**（`_reuse_connection` 先 `connect` 再 `add`，注册表里不出现未连接连接）：停机快照因此总能拿到 socket 取消在途 I/O，停机后也不可能再经建连或 `Connection: close` 自动重连路径发出请求；建连带独立上限（10s），阻塞 connect 也在确认窗口内结束。正常（自然收尾）不中断在途请求，请求正常完成。

**边界**：

- `ctx.poll` 中停机（`stop` 触发）返回 `PollResult(status="stopped")` 且不记录——停机截断轮询不算失败；
- 引擎超时中断（`interrupt`）时在途请求以 `error_type=stopped` 返回——只有被中断（TIMEOUT）case 的记录会含该类型，其 records 随超时产物被丢弃，不进入求值证据；
- 终端 4xx（除 408/409/425/429）立即判 failed，传输错误继续轮询到 deadline（对齐 `poll_commit`）；
- 阶段函数内不应再注册新阶段（阶段快照在开始时已排序）。

## 6. 画像契约（`profiles/*.yaml`）

```yaml
name: str                 # 必填
description: str
target:
  base_url: str           # 必填，支持 ${ENV:-default} 展开
  headers: {k: v}         # 公共头（同样展开）
  read_timeout_s: float   # 默认 30
load:
  workers: int            # 总 worker 数，默认 8
  duration_s: float       # 秒；0 = 直到 Ctrl-C，默认 60
  mix: {task: weight}     # 任务名 -> 权重；缺省等权
  arrival: {task: {model: none|fixed_rps|poisson, rps, ramp_s}}  # 按任务到达门
tenants: [{name, headers}]  # 多身份；缺省单租户（只用 target.headers）
params: {自由键}           # 场景特有参数，场景代码经 ctx.params 读取
```

校验（`profile.py`）：`base_url`/`name` 必填；workers≥1；mix 权重非负且不全零；arrival model 合法、`fixed_rps` 要求 rps>0；顶层只接受 `{name, description, target, load, tenants, params}`，其余报 `unknown profile fields`——`params` 是唯一自由容器。

## 7. 引擎行为（`engine.py`）

- **worker 分配**：`split_workers(total, weights)` 按权重整数拆分，首任务 `round`、末任务吸收余数（对齐 `loadgen.split_threads`）；`mix` 引用了场景不存在的任务名报错；
- **租户绑定**：worker `worker_idx % len(tenants)`；请求头 = target.headers + 租户 headers；
- **到达门**：`RateGate`（`fixed_rps` 精确调度 + sqrt 爬坡 / `poisson`），按任务名配置，`none` 打满；
- **阶段注入**：主线程按 `at_s` 排序触发 phase；phase 执行于临时线程池（`max_workers`），其 ctx `worker_id=-1`、`extra=phase.name`（D 场景 phase 名 `burst` → 记录 `extra="burst"`）；`tenant_counts` 阶段为每个租户建独立 ctx、展开 job，同一并发阶段内跨租户并行执行（barrier 语义，见 §9.1）；
- **worker 异常**：任务函数抛出的异常记一条 `op="transaction"`、`error_type="other"`、`detail` 带异常信息的错误记录，worker 继续；
- 场景/画像不匹配（mix 未知任务）在 `run()` 时抛 `SceneError`。

## 8. 记录字段（`records.py`）

`RequestRecord` 字段与 legacy `loadgen.RequestRecord` 逐项对齐（scene/worker_id/tenant_idx/op/stage_ms/status/error_type/ts_ms/http_status/session_id/archive_id/extra/retry 系列/message_id/content_hash/content_bytes/hit_count/real_recall/quality_ok/degraded/query/reason_code/retry_after_s），另加 `detail`（worker 异常上下文）。`CSV_FIELDS` 定义导出顺序；`report.py` 按 op 聚合 latency/错误/状态，写 `summary.json` + `records.csv`。

**报告聚合**（`report.py`）：

- `summarize` 除按 `op` 聚合外，同时按 `tenant_idx` 分组输出 `summary["tenants"]`——每租户一段 `{tenant_idx, name, count, ok, fail, rps, latency_ms, error}`（对齐 total 结构），`print_summary` 渲染租户对比表，用于租户公平性分析；
- 场景模块可选导出 `report(result, profile) -> dict`：返回该系统特有的分析（如 EchoMem 的 `quality_ok` 占比、命中量分布），`run` 时合并进 `summary["custom"]` 并打印。**分析语义归 targets，通用层只负责分组与运输**——它不认识 `quality_ok`，只是记录字段原样透传。

## 9. 四场景无损翻译对照

翻译基准为 legacy 压测体系 `loadgen.py` 与 `scenarios.py` 的原语义，默认参数取自 `run_stress.py`（top_k=5、messages_per_session=10、commit_poll_timeout=600、burst_commits=32、burst_window=10、commit 不重试）。

| 场景 | 文件 | 原语义 → 场景表达 | 验证 |
|---|---|---|---|
| A 纯读 | `targets/echomem/scenes/scene_a_pure_read.py` | 全部 worker 循环 `POST /api/retrieval/search`（query 池轮询、agent_id 空、top_k 来自 params）；每请求记录 + 锚词质量规则 | `test_scenes::test_scene_a_*` |
| B 纯写 | `targets/echomem/scenes/scene_b_write_injection.py` | 事务 = open→add×N（末条带 PERFTAIL anchor）→commit_submit→poll commit_done（600s）；四阶段独立计时；add 失败即事务失败；commit 不重试（与 `--commit-retry-max 0` 一致） | `test_scenes::test_scene_b_*` |
| C 混合 | `targets/echomem/scenes/scene_c_mixed.py` | `tasks={read, write}` + `load.mix`（如 read=8,write=1）按权重拆 worker 并发 | `test_scenes::test_scene_c_mixed` |
| D 洪峰 | `targets/echomem/scenes/scene_d_burst.py` | 持续读 + `schedule` 在 `delay=max(0,duration-window)/2` 处注册 `at_time`：burst_commits 个写事务、max_workers=8、单租户、`extra="burst"`、seq 与主负载共享 | `test_scenes::test_scene_d_burst` |

与原文的已知差异（语义无损、量纲一致）：

- 原 `run_stress` 的 worker 总数 = 租户数 × 每租户并发；新框架 `load.workers` 直接给总数，租户经 `profile.tenants` 绑定——同一数值下并发拓扑等价；
- 种子数据（`prepare.py` 灌入、保证索引有内容）不在场景语义内，由用户自行灌入；场景用自带 query 池（`params.queries`）；
- `commit_retry_max>0` 的重试逻辑原为 `run_write_transaction` 内置；新框架默认为 0（不重试），需要重试时在场景代码里用 while/try 表达（普通 Python）。

### 9.1 正式验收场景（自 legacy loadgen 语义翻译）

正式验收（barrier / 多波洪峰 / 容量）复用通用引擎，场景文件只表达注入拓扑，负载量纲（rps、并发、时长）由画像 `params`/`arrival` 控制：

| 场景 | 文件 | 语义 | 验证 |
|---|---|---|---|
| commit barrier | `scenes/scene_barrier.py` | 读负载跑满 duration；`schedule` 注册一次跨租户写事务阶段：`barrier_count` 个事务按 `barrier_distribution`（uniform/zipf/explicit）展开为 `{tenant_idx: count}`（`targets/echomem/_barrier.py::barrier_tenant_counts`），同一并发阶段内并行提交（`barrier_max_workers`）；`barrier_waves` 多波 + `barrier_cooldown_s` 间隔；`floor_to_tenants` 时每租户至少 1 个。阶段 `extra="barrier"` | `test_formal_scenes::test_scene_barrier_*` + `test_barrier_*`（分布数学） |
| 多波洪峰 | `scenes/scene_burst_waves.py` | D 的多波扩展：在 `delay=max(0,duration-window)/2 + wave*cooldown` 处注册 `burst_waves` 个 `count=burst_commits` 的写事务波，各波 `extra="burst"` | `test_formal_scenes::test_scene_burst_waves` |
| 容量 | `scenes/scene_capacity.py` | `tasks={read, write}` 混合（baseline/mixed/commit-storm/search-storm/soak/capacity-N 共用），负载差异只在画像 `arrival`（`commit_rpm/60 → read rps`）；K 档单租户 | `test_formal_scenes::test_scene_capacity_mixed` |

边界：barrier 的租户分布校验（uniform 余数给前几个、zipf 权重 1/rank^s 归一取整余数补首位、explicit 求和须等于 `barrier_count`）对齐 legacy `loadgen._barrier_tenant_counts`，非法输入由 `at_time` 抛错并记 `op="transaction"` 错误记录。

## 10. CLI

`python -m performance`（需在仓库根运行，包在根下）强制带 `--target <system>`，
按 §17.5 转发到 `targets/<system>/main.py` 或 `observation_run.py`（文件存在性
回退，见 §17），不带 `--target` 退出 2。通用场景
引擎是 `targets/general` 这个 target 的 CLI，子命令跟在 `--target general` 后：

- `run --scene <scene.py> [--profile <profile.yaml>] [--out] [--base-url] [--workers] [--duration] [--mix read=8,write=1] [--strict]`，例：`--scene targets/echomem/scenes/scene_c_mixed.py --profile targets/echomem/profiles/echomem.yaml`
- `validate --scene <scene.py>`：导入并检查任务契约
- `list [--dir <scenes/>]`：默认扫全部 `targets/<system>/scenes`（显示 `system/scene` 前缀）；显式 `--dir` 时扫指定目录。两类都跳过 `_` 开头辅助模块；**不扫探针**（见 §13.4）
- `probe --scene <probe.py> [--profile <profile.yaml>] [--base-url] [--out]`：单次执行探针并报告四态（契约见 §13）

不针对具体系统的临时场景/探针放 `targets/general/scenes`、`targets/general/probes`，
结果按场景位置落到 `targets/general/results`。`--strict` 在任何请求失败时以退出码 1 结束。

## 12. 边界与限制

- 场景/画像引用不匹配在 run 时暴露（`SceneError`），不静默；
- phase 内注册新 phase 不会被本轮执行（快照语义）；
- `duration_s=0` 时无限运行直到 Ctrl-C，阶段仍按 `at_s` 触发；
- 单机单进程模型：worker/phase 同进程内线程，指标不经外部采样（与 legacy 压测体系的 `/metrics` 观察层无关）。

## 13. 探针执行模型（`targets/<system>/probes/*.py`）

压测场景只有两种类型：负载场景（§2-§12，持续打流量、度量延迟）与探针（本节，
只跑一次、验证行为）。探针文件必须导出 `run(ctx)`，可选 `exit_on`；框架执行一次、按四态汇总、
决定报告与退出码——系统作者只写检查逻辑。探针是系统特有的，放在各被测系统子包下；
`probe.py` 完全通用（不认识任何具体系统）。`targets/echomem/probes/` 的 14 个执行
探针（capability / blackbox_contract / missing_cases / concurrent_commit /
invalid_input / fault_isolation / limit_failure_sweep / commit_recovery /
tenant_observability / fault_suite / nxn_isolation / disconnect_recovery /
concurrency_topology / payload_boundary）
全部经编排器（§17.4）的 `PROBE_NAMES` 注册表接线，保持原 JSON 报告 schema 与四态语义；
`fault_injection` / `cursor_reconcile` / `recovery` 是 fault_suite 的进程内原语
（同为 probe 模块，不单独接线，随 fault plan 运行）。
`nxn_isolation.py`：N×N 租户隔离，每 writer 写私有 marker 提交后，逐 (writer, reader)
对验证同租户命中/跨租户不命中，经真实 per-tenant `X-Auth-Key`，四态报告；
`nxn_writer:N` 仅在 writer 阶段中断时以 INCONCLUSIVE 出现，成功 writer 并入总
`nxn_isolation` 的 detail 计数。`disconnect_recovery.py`：非破坏性恢复验证——断开目标
进程连接后检查同 key 消息重放可恢复，INCONCLUSIVE 不在 `exit_on`（数据采集型）。
行为移植：`capability` 支持 `cursor_uri_template`（经 `/fs/read?uri=` 读 echo://
文档解析 commit cursor）；`commit_recovery` 支持 `pid`/`restart_command` 直接杀进程、
source 顺序对账（order_status）与幂等重放细化（same_archive 未重放 → INCONCLUSIVE）；
`fault_isolation` 的 `control` 把 `target_tenant` 注入 HTTP body 与 command format，
且用 try/finally 保证故障结束后必执行 disable；`limit_failure_sweep` 的 workers
按 level 封顶（`max(1, min(level, workers))`）。

### 13.1 契约

- `run(ctx)`：执行一次；内部用 `ctx.post/get/poll` 发真实请求，用 `ctx.check` 记录断言；
- `ctx.check(name, *, status, reason, elapsed_s, detail)`：status ∈ PASS / FAIL /
  NOT_IMPLEMENTED / INCONCLUSIVE。探针 ctx 与场景 ctx 同源（请求/记录语义一致，
  仍可 `ctx.note`/`ctx.record`），只是多出 checks 列表；场景 ctx 上调用 `ctx.check`
  抛 `RuntimeError`；
- `exit_on`：可选元组，决定哪些状态使进程退出码为 2；默认
  `("FAIL", "NOT_IMPLEMENTED", "INCONCLUSIVE")`（任何非 PASS 都算失败）。
  数据采集型探针可设为 `()`（恒 PASS、退出码恒 0）；恢复型探针可把
  INCONCLUSIVE 移出退出条件（如 `disconnect_recovery`）。

### 13.2 四态语义

- `PASS`：已观测到符合预期；
- `FAIL`：已观测到不符合预期；
- `NOT_IMPLEMENTED`：显式 HTTP 404——唯一可证明「未实现」的证据；
- `INCONCLUSIVE`：缺少部署方提供的故障/恢复控制、凭据或端点，无法观测。探针不得
  把自身缺少适配器当成对系统能力的否定。

`overall_status` 聚合序：FAIL > INCONCLUSIVE > NOT_IMPLEMENTED > PASS（探针不得在
未能观测时声称 PASS）。

### 13.3 报告

`summarize_probe` 保持原探针 JSON schema：`status` / `created_at` / `base_url` /
`real_http` / `mock_model` / `probe` / `checks` / `summary`
（total/pass/fail/inconclusive/not_implemented），下游消费者无需改动。参数经 profile
的 `params` 段传入（键名与原 CLI `--xxx` 同名），`base_url` 在 `target.base_url`
（可 `--base-url` 覆盖）。

### 13.4 CLI

```bash
python -m performance --target general probe \
  --scene <probe.py> [--profile <profile.yaml>] [--base-url <url>] [--out <json>]
```

退出码：`0`（overall 不在 `exit_on`）/ `2`（在 `exit_on`）。`list` 只扫
`targets/*/scenes`，探针不参与（探针是显式逐条运行的检查，不是可枚举的负载场景）；
echomem 入口的选择交给编排器注册表 `PROBE_NAMES`（`--probes`，见 §17.4/§17.5）。

## 14. 如何新增一个被测系统

不针对具体系统的临时压测不需要建 target：场景/探针直接放 `targets/general/`
（`scenes` / `probes`，见 §10）。接入新 agent/记忆系统时，通用层
（engine/ctx/records/profile/stats/report/run）零改动。步骤：

1. **建包**：`targets/<system>/` + `__init__.py`（targets 下每个系统一个自包含子包）。
2. **写协议适配** `targets/<system>/protocol.py`：
   - **端点级函数**：每个 HTTP 端点一个函数，签名 `fn(ctx: Ctx, ...) -> Response`（或 `PollResult`），内部用 ctx 原语发请求、套本系统请求/响应约定、记录质量字段（`ctx.note`）；解析辅助（如取 body 中的 id、判断锚词）也放这里；
   - **标准任务**：把端点组合成事务的任务函数（对齐本系统在 legacy `loadgen.py` 里的读/写事务），新场景直接复用。
3. **写场景** `targets/<system>/scenes/scene_*.py`：从 protocol import 端点/标准任务，导出 `task` 或 `tasks`（可选 `schedule`，契约见 §4）；如需系统特有分析报告，再可选导出 `report(result, profile) -> dict`（合并进 `summary["custom"]`，见 §8）。
4. **可选探针** `targets/<system>/probes/*.py`：导出 `run(ctx)`（契约见 §13），验证单次行为；从 protocol 或 `_client.py` import 端点级函数。
5. **可选画像** `targets/<system>/profiles/*.yaml`：默认 base_url、headers、params 等，供 `run --profile` / `probe --profile` 使用。

`--target general list` 默认扫 `targets/*/scenes` 自动发现新系统；`test_all_target_scenes_load` 会验证其场景可加载。场景文件不需要 `__init__.py`（引擎按文件路径加载）；`targets/<system>/` 需要（场景内 `from performance.targets.<system>.protocol import ...` 走包路径）。

### 15.1 preflight 门禁语义

- `parse_engine_configs` 同时接受扁平 `engines` 数组与 EchoMem 原生嵌套 config：递归发现
  `{api_base, model}` 形态的 provider 映射；**跳过** `enabled=false` 分支（未启用不算运行时
  配置）、`provider∈{fake,mock}` 模板与缺 `api_base`/`model` 的条目（原生 config 里的假
  VLM/纯模型模板不是真实 provider endpoint，不得让真实模型预检失败）；**跳过非活跃的
  intent LLM**——原生 config 的 `search.intent.backend` 非 llm/model/openai_compatible
  时，`recall.model.intent_llm` 不是运行时 provider，预检它会让有效运行误中止；去重后返回
  `{id, kind, api_key_env, api_base, model}`。kind 推断：显式 `llm/embedding` 或按 id 是否含
  `embedding/vector/query_embedding`。
- `check_env`：每个引用的 `api_key_env` 变量必须存在且非空。
- `probe_endpoint`：对 `kind=llm` 发 `{api_base}/chat/completions`、`embedding` 发
  `/embeddings` 一次最小真实请求（`max_tokens=1` / `input=ping`）；2xx = 模型名被接受，
  HTTP 错误/超时 = 失败，返回 `{status: ok|error, code, elapsed_s, model_supported, error}`。
- `config_digest`：对端点/模型名做 SHA-256，**绝不把 API key 值纳入摘要**。
- `run_preflight` 返回 secret-free 结构（含 `probe_attempts`）；`ok=False` 时调用方必须中止
  运行并把结果归类为环境/依赖错误。**transient 重试**：连接类瞬时失败（DNS 解析失败、
  超时、connection refused、network unreachable 等 `_retryable_probe_failure` 命中项）
  按 `retry_attempts`(3) 线性退避重试；确定性 HTTP 错误（code 非 None）永不重试。

### 15.2 观测求值（`observation.py`）

`evaluate_observation(suite, profile, m1_reports, *, quick, selected_metrics)` 对
选中的指标各给 `{status, reason, observed, ...}`，status ∈ MEASURED / PARTIAL /
BLOCKED / INCONCLUSIVE / EXECUTION_ERROR；降级只把状态推向 INCONCLUSIVE/PARTIAL/
BLOCKED，绝不把缺失证据推断成 PASS/MEASURED（见 §17.6）。`write_observation_report`
渲染自包含静态 HTML。`summarize_m1` 聚合容量探索报告（qps/延迟/资源/崩溃恢复），
`summarize_m2` 做公平性窗口（Jain 指数、最慢租户额外等待），`summarize_m4` 汇总
fault-isolation 采样矩阵，`summarize_api_coverage` 统计探针 API 覆盖。

### 15.3 metrics：/metrics 观测语义

- `parse_prometheus_text`：跳过 COMMENT/TYPE/HELP 与 `EOF` 之后内容；histogram 系列保留全名
  （`name_bucket/_sum/_count`）；同 name+labels 的后续样本覆盖前者；畸形行静默跳过。
- `MetricsMonitor`：后台 daemon 线程每 `interval_s` GET `<base_url>/metrics` 保帧；
  抓取/解析失败计 `fetch_failures` 并记 `last_error`，**不中断采样**；`sample()` 也可手动调用。
- 派生分析全部基于已保帧（`frames`）的**窗口查询**，不触发新请求：`counter_delta`（窗口
  起点取窗内最早帧、回退到窗前最后一帧，端点缺失 → None）、`gauge_max`/`gauge_series`、
  `cpu_utilization_series`（相邻帧差 / 墙钟跨度，首帧无差跳）、`histogram_percentiles`
  （取窗内最后一帧的累计桶分布做线性插值，空窗/零总量 → 全 None）、`cpu_utilization`。
- `scene_resource_summary`：一个场景窗口的资源快照（CPU/RSS/线程/句柄/inflight/队列深度/
  三段 latency 分位），缺指标时对应键为 None，容忍缺失。
- **PR421 B7 覆盖**：`LANE_METRIC_FAMILIES`（lane 四元组 4 族）+ `FANOUT_METRIC_FAMILIES`
  （fan-out 二元组 2 族）是家族→短名单一事实源（探针侧 `limit_failure.metrics_coverage`
  复用同一常量，见 §13）；`match_metric_family` 接受 `_bucket/_count/_sum` 后缀样本名；
  `metric_coverage(monitor, t0, t1)` 从帧推导 `present/missing/lane_quartets/
  fanout_engines/bounded_label_violations`（lane 指标出现 `tenant_id`/`tenant` 标签即违规，
  上限 5 条）——与探针侧同构，是观测报告 `details.pr421_metric_coverage` 的证据来源。
- `write_metrics_csv`：帧 → 长表 `metrics_samples.csv`（ts, metric, labels, value），
  供报告与事后重渲染。
- **case 级采样接线**（`runner.run_case`）：`metrics_enabled` 时在每个 case 执行前后
  start/stop `MetricsMonitor`（interval 2s），写 `metrics_samples.csv` 并给
  `summary.details.pr421_metric_coverage` 挂覆盖证据；`collect_metrics=False` 或
  base_url 为空则完全跳过。
- histogram 跨 label 集按桶上界合并（全局分布，忽略 outcome/status 标签）。

### 15.4 capacity_seed：租户种子与语义种子

- `prepare_actors`：经 `probes/_client.py` 的 `EchoMemHTTP`（`provision_isolated_identity`
  / `load_tenant_specs` → `TenantSpec`）准备租户 actor；每个 actor 带唯一锚词 marker
  查询（写读一致性探针的查询池），**种子注入不计入被测负载**——只保证检索索引有真实内容。
- `observe_recovery`：M1 容量探索的崩溃恢复观测（杀进程后重跑探测，验证可恢复）。
- 语义种子：runner 的 `_prepare_semantic_seed` 钩子（通用层 `suite.py` 的 seed 钩子，
  `kind` 默认 `synthetic`，profile 可覆盖）构造固定事实语料，灌种后**真实执行检索验证
  事实可命中**（healthy 数 < 预期 → `SeedPreparationError`，绝不静默跳过）；`reuse_seed`
  （`semantic_seed_cache`）复用已校验的种子缓存，避免重复灌种。
- 复用 `probes/_client.py` 的 `load_tenant_specs`，不另造客户端。

### 15.5 report_html：数据报告

- 输入：manifest（声明各 run 的元数据/门禁）+ 每 run 的 `summary.json` + `commit_results.csv` +
  `search_results.csv` + `server_metrics.csv`；输出：自包含静态 HTML（无外部资源依赖），
  `render(manifest_path, output_path)`。
- `normalize_row` 把 CSV 行按 op 归一为结构化字段（时间戳/数值容错）；`group_runs`/
  `time_buckets`/`tenant_groups` 做分组；`acceptance_block` 渲染门禁判定；`detail_block`
  渲染单 run 明细；缺失数据容错（`float_value`/`int_value` 返回 None 而非抛错）。

## 16. 求值器（`targets/echomem/acceptance/` 的 evaluate / observation / 证据模块）

运行产物的**判定核心**：把 manifest / suite / 探针结果判为 PASS / FAIL / INCONCLUSIVE /
NOT_IMPLEMENTED（观测入口另有 MEASURED / PARTIAL / BLOCKED）。各模块都是纯判定、
无 I/O、无 CLI（CLI 归编排器），只消费 JSON 数据。

### 16.1 evaluate：PR421 验收矩阵（`evaluate.py`）

- 常量：四态 + `PR421_LANES`（5 个预期 lane：recall_engine / recall_intent_llm /
  recall_query_embedding / recall_rerank / commit）+ `PR28_REVIEW_RESOLUTION`（评审意见
  闭环，与可测门禁分开保存——harness 项已解决不代表 EchoMem 能力可用）。
- `evaluate_pr421_acceptance(manifest)` 跑 8 个可测门禁：

| 门禁 | 判定依据 |
|---|---|
| Search success rate | 同并发档 A 基线先达 99% 成功率；压力场景成功率门限（超时单列） |
| report(6) Search quality assertion | marker Search 的确定性断言证据（真实召回，非 HTTP 200 冒充） |
| Search P95 isolation ratio | 压力/基线同并发档 P95 隔离比 ≤ 1.20，排除超时样本 |
| Tenant fairness (Jain) | ≥2 个独立认证租户的 Jain ≥ 0.90 |
| Accepted Commit eventual completion | 已接受（202）commit 最终完成率 1.0 |
| Saturation rejection rate | 拒绝率 ≤ 0.05、拒绝延迟 ≤ 1.0s，且响应带 429/503 + Retry-After + reason_code |
| Hot-tenant bystander fairness | 热租户旁观：热租户负载下旁观租户读 P95 劣化 ≤ 1.50 |
| B7 lane/fan-out metrics | 全部指标族、预期 lane 四元组与 fan-out 有服务端证据（`PR421_LANES`） |

- 能力缺失的门禁明确判 INCONCLUSIVE 而非通过：cursor/message-set、Kill-9
  local/cluster recovery、fault control（`artifact_gate`/`capability_gate` 从
  fault_suite / capability_probe 取证据，缺配置给默认 reason）。
- overall 聚合序：FAIL > {INCONCLUSIVE, NOT_IMPLEMENTED} > PASS。
- 输出含 `pr28_review_resolution` 与 `review`（reasonable / missing_or_weak targets，
  供评审闭环）。
- `build_model_analysis_input(manifest, acceptance)`：**有界、secret-free** 的外部 LLM
  诊断上下文——只给证据、禁止虚构服务端行为、区分四态、指明改 EchoMem 代码/部署/平台。

### 16.2 观测求值（`observation.py`）

按 §15.2 的 `evaluate_observation` 汇总，缺测量 / 降级路径保持四态诚实：
M1 无容量证据 → BLOCKED/INCONCLUSIVE；M2 单租户无公平性可比 → INCONCLUSIVE；
M3 种子失败 → INCONCLUSIVE；M4 故障控制面缺失 → INCONCLUSIVE 命令 + BLOCKED；
M5 无 kill-9/恢复控制 → INCONCLUSIVE；M6 无 tenant-observability → INCONCLUSIVE。
`summarize_api_coverage` 只统计探针实际请求过的 API，不把未测面当通过。

### 16.3 M5/M6 证据计数（`reliability_evidence.py` + `observability_timeline.py`）

- `recovery_counts(sample_or_aggregate)`：M5 恢复样本聚合——`status`（FAIL >
  INCONCLUSIVE > PASS）、`failed_samples`、去重后的独立归档数、planned/unknown
  计入分母；恢复检查出现失败即 FAIL（子样本 FAIL 覆盖父 PASS）。
- `observability_counts(...)`：M6 四元组样本计数——每租户每 lane 单元格的
  valid/duplicate/missing/invalid 统计、`repeat_observations` 逐次快照明细、
  重复快照去重、预期重复数（expected_repeats）与实际通过的 `passed_repeats`
  对比（不足 → INCONCLUSIVE）；任何输出都不导出 `private-` 前缀标识符。
- `timeline_counts(evidence)`：M6 时间线核验——before/during/after 三窗口快照、
  `max_sampling_gap_s` 与 `gaps_exceeded`、counter 对比次数；中间快照缺失不可被
  完整末帧掩盖（INCONCLUSIVE）。

### 16.4 M1/M3 种子与容量（`capacity_seed.py` + `capacity_experiment.py`）

- `capacity_seed.prepare_actors`：M1/M3 的租户 actor 与 marker 查询（§15.4），
  `select_reused_actors` 在恢复观测中复用已就绪 actor，避免重复开通。
- `capacity_experiment` 系列（capacity_experiment / capacity_load /
  capacity_recovery / capacity_statistics）：M1 容量探索——arrival_plan、
  wilson 分位、qps 基线、崩溃恢复观测、资源数值与 config 摘要，产出容量报告供
  `summarize_m1` 消费。

## 17. 编排器（`targets/echomem/observation_run.py` + `orchestrator/`）

观测入口编排（M1-M6），对应 legacy 压测体系 objective_suite / formal_suite /
regen_report 三者合并后的 CLI 编排职责；场景执行不再有子进程边界（legacy
formal_suite → run_stress 的 150+ CLI 参数链被进程内 Engine 取代），探针仍以
`python -m performance --target general probe` 子进程运行（隔离探针崩溃）。
`run.py --target echomem` 经 `performance/dispatch.py` 按
`targets/echomem/{main,observation_run}.py` 文件存在性回退，落在 observation_run。

### 17.1 模块划分

| 模块 | 职责 |
|---|---|
| `../../suite.py` | 通用套件能力：`summarize_case_records`（records→metrics 契约摘要）+ `run_case`（Engine 单 case 执行 + summary/records 写盘）；op 映射/锚点/summarize/证据可参数化；`QuickSpec`/`apply_quick`（quick 收敛）、`build_case_profile`（case→Profile 骨架）、`SeedContext`、`run_suite`（prepare→preflight→灌种→逐 case→acceptance 全流程，select_cases/build_profile/run_case/preflight/seed/evaluate 六钩子） |
| `../../probe.py` | 通用探针执行：`run_configured_probe`（临时 YAML 写入→`probe` 子进程→产物读回→状态保留的统一骨架）、`write_probe_profile`/`probe_command`/`preserve_probe_status` |
| `suites.py` | 观测场景矩阵（`six_metric_observation_cases`：6 例，M2 公平性 2 例 + M3 洪泛 4 例）+ case → Profile 解析（`build_case_profile`）+ barrier 参数翻译（`_apply_barrier_params`，仅 barrier 分支） |
| `runner.py` | 观测套件执行（经通用 `suite.run_suite` 钩子）：`six_metric_observation_cases` 过滤为 `_select_cases`、语义种子钩子 `_prepare_semantic_seed`（synthetic kind + reuse）、`run_case` 挂 echomem 的 details/parameters 扩展、commit/search 证据 CSV 与 case 级 /metrics 采样 |
| `probes.py` | 14 类配置化探针编排：`PROBE_NAMES` 注册表 + `--probes` 选择过滤（指标必需探针不可排除），统一走通用 `run_configured_probe`，仅保留 fault plan 物化与各段 passthrough 键 |
| `commit_diagnostic_report.py` | 独立图表工具（不依赖观测报告）：从 concurrency_topology 矩阵渲染 Commit 诊断图（含双轮对比），供 `scripts.build_commit_diagnostic_report` 使用 |
| `../observation_run.py` | CLI：profiles/env 加载（`load_profiles`/`_resolve_profile` 展开 `${ENV:-default}` 并把相对路径解析为绝对）、`--metrics`/`--scenarios`/`--probes` 解析、M4/M6 依赖窗口补齐、输出锁、观测报告发布 |

### 17.2 场景矩阵（`suites.py`）

- case 结构：`{label, scene, tenants, duration_s, search_rps, commit_rpm,
  sessions_per_tenant, messages_per_session, commit_barrier* 系列, quick_commit_rpm,
  search_workers/commit_workers/read_only, fairness_bounded}`；
  `scene` 是 scenes/ 下的场景文件名。`six_metric_observation_cases(*, quick=False)`
  是显式常量列表：M2 公平性 2 例（m2-fairness-4t / 8t）+ M3 洪泛 4 例
  （m3-baseline / m3-flood-uniform / m3-flood-single-tenant /
  m3-heterogeneous-tenants），label 即 `--scenarios` 目录（§17.5）。
- `build_case_profile` 翻译：`arrival` 按任务映射 fixed_rps（search_rps → read、
  commit_rpm/60 → write，rps>0 且场景含该任务才加）；barrier 字段翻译为
  ctx.params（barrier_count/distribution/zipf/waves/cooldown/max_workers，
  fairness-bounded+uniform 时 floor_to_tenants=True）。
- `_apply_barrier_params` 只处理 scene_barrier 分支（D 场景 burst 分支已随旧矩阵
  删除，burst 能力仍由 scenes/d_burst.py / burst_waves.py 提供）。
- `apply_quick` 收敛（通用层）：duration 双 cap；barrier_count = min(原值,
  min(全局 cap, case quick_barrier_count_cap))，explicit 分布超 cap 时按比例缩放；
  quick_commit_rpm 非 None 时覆盖 commit_rpm；sessions 压到 1。

### 17.3 套件执行（`runner.py` + 通用 `suite.py`）

- `run_suite(profile, ...)` 流程：prepare_command（如有）→ readiness 门禁
  （`acceptance/readiness.check_readiness`，`strict=bool(profile["six_metrics_observation"])`）
  → 语义种子钩子（`_prepare_semantic_seed`，synthetic kind + reuse）→ `_select_cases`
  逐 case（`six_metric_observation_cases(quick=...)` 按 `scenarios` label 过滤，经通用层
  `suite.run_case`）→ `evaluate_pr421_acceptance` → 写 suite.json / acceptance.json。
  prepare/seed 失败时先经 evaluate 求值再写盘，`evaluate` 缺省时 acceptance 记 NOT_RUN。
- `run_suite` 的 `resume=True`（CLI `--resume`）支持中断续跑：按目录顺序检查
  每个 case 的 `suite_dir/<fs_safe_label(label)>/summary.json`，存在且可解析即视为
  已完成——跳过执行，把历史 run 从盘上重建（`_load_completed_run`，字段对齐
  `run_case` 返回结构）合并进 manifest；从第一个未完成 case 继续。summary.json
  缺失/损坏则重新执行。历史 + 本次 runs 一起经 `_finalize_suite` 写盘，
  求值证据因此完整。
- 通用层 `suite.summarize_case_records` 把 records 汇总为 metrics 契约摘要（对齐
  求值器输入契约）：op 映射参数化（默认 read→search、commit_submit→commit.submitted、
  commit_done→commit.completed），`is_anchor` 回调为 None 时 quality_asserted 记 0；
  search 延迟转**秒**单位（stage_ms/1000）；quality_failures=quality_ok 失败的 read；
  fairness.commit_completed_per_tenant 与 per_tenant 按 tenant_idx 聚合；
  rate_limited_count 按 reason_code 限流语义。
- 通用层 `suite.run_case` 执行单 case（load_scene + Engine.run，ENV_ERROR/TIMEOUT
  语义），写 summary.json / records.csv（`report.write_records`）；runner 侧薄包装
  挂 `summarize`（补 echomem 的 details/parameters）与 `write_evidence`
  （commit_results.csv / search_results.csv）。
- **case 超时回收**（`run_case` 的 `timeout_s`）：Engine.run 在守护线程执行，
  超时记 `TIMEOUT` 并调用 `Engine.stop()`——先置 `interrupt`/`stop` 事件，
  再有界 shutdown 本 Engine 连接注册表里连接与在途响应句柄的底层 socket
  （`Connection: close` 摘除 `conn.sock` 后 socket 由响应持有，响应句柄覆盖
  该窗口；不等缓冲响应读取，停机调用本身不阻塞），后有界等待
  `_STOP_CONFIRM_S`（30s）确认退出；注册表关闭守卫让停机后迟到的连接/响应
  注册立即被关闭并拒绝（stopped），worker 不再进入 I/O——stop 与 worker
  退出均有界、不依赖服务端结束响应；连接登记前必已建连（建连带独立上限），
  已登记未连接与 `Connection: close` 后自动重连的路径在停机后不可能发出
  请求；summary.json 持久化真实 `status` /
  `runner_timeout`，`--resume` 只复用明确完成且证据完整的 case。确认窗口到期
  worker 仍存活时，先持久化 TIMEOUT 产物再抛错中止套件——**绝不在旧 worker
  存活时推进下一 case**（fail-closed）。Engine 正常收尾（含异常路径）在
  `run()` 的 finally 关闭并注销本 Engine 全部连接与残留响应，顺序 case 不跨
  进程累积客户端描述符。
- `metrics_enabled`（instance profile，默认 true）控制 case 级服务端 /metrics 采样：
  每个 case 运行窗口内 `MetricsMonitor` 后台采样，写 `metrics_samples.csv` 并把
  `details.pr421_metric_coverage` 挂到该 run 的 summary（观测证据，§15.3）。
- 每 case 输出目录含 summary.json / commit_results.csv / search_results.csv /
  metrics_samples.csv（采集开启时）/ records.csv；commit_results.csv 的 completed
  行是探针层 `_first_completed_commit_csv` 的文件系统证据源。

### 17.4 探针编排（`probes.py`）

`run_configured_probes(profile, *, probes=None)` 按 profile 配置段执行 14 类探针
（capability_probe / blackbox_contract / missing_cases / concurrent_commit /
fault_isolation / limit_failure_sweep / commit_recovery / fault_plan /
tenant_observability / nxn_isolation / disconnect_recovery /
concurrency_topology / payload_boundary / invalid_input），统一契约：写临时
YAML → `python -m performance --target general probe --scene <probes>/<scene>.py
--profile <tmp> --out <out.json>` 子进程 → 读产物 → 删临时文件；缺前置条件
（如 blackbox 无 commit_csv+tenant_path）记 INCONCLUSIVE 制品。

**选择语义**（`--probes`）：

- `probes=None`：跑全部已配置的探针块（保持配置驱动现状）；
- `probes` 给定：只跑 `选中的 ∪ 指标必需的`——指标必需集由 `_configure` 按
  profile 配置态决定（M4 → fault_isolation、M5/M6 → commit_recovery、
  M6 → tenant_observability），**指标必需探针不可被 `--probes` 排除**；
- 选中但无配置段的探针以空配置运行（探针自带安全默认参数）；
- 未选中且非指标必需的探针块完全跳过：不运行、不产生 INCONCLUSIVE 命令记录；
- 注册表 `PROBE_NAMES`（14 名）在编排层校验，未知名直接报错，`--help` epilog
  列出全部可选值。

fault plan 的 `${BASE_URL}` 占位在编排层替换为实际 base_url。各调用块统一走通用层
`performance.probe.run_configured_probe`，编排层只保留 fault plan 物化与各段的
passthrough 键：fault_isolation 透传 `target_tenant`/`bystander_tenants`/`endpoint`/
`command` 等，commit_recovery 透传 `container`/`pid`/`restart_command` 等（探针行为
见 §13）。fault_suite 块特殊：探针自行写 `out_dir/fault-suite.json`，编排层单独读
该文件并保留探针状态。移植探针接线：`nxn_isolation` 段（键 `nxn_isolation`）透传
`markers_per_tenant`/`timeout_s`/`commit_poll_timeout_s`/`auth_header`，
`disconnect_recovery` 段（键 `disconnect_recovery`）透传 `requests`/`auth_key_env`，
pid 取自 `resource_evidence.process_id`，tenant 取自 tenant_config 首个租户。

### 17.5 CLI（`observation_run.py`）

`python -m performance.run --target echomem`（`performance/dispatch.py` 回退到
`targets/echomem/observation_run.py`）：
`--profiles <json> [--profile <name>] --out-dir <dir> [--metrics M1,M2,M3]
[--scenarios <catalog 子集>] [--probes <PROBE_NAMES 子集>] [--quick] [--resume]
[--timeout-s 7200] [--env-file <env>]`。

- **`--metrics`**：选指标（默认 M1,M2,M3）。选中的指标决定默认负载场景
  （M2 → 公平性 2 例，M3 → 洪泛 4 例，M4/M6 额外补依赖窗口）与默认探针必需集。
- **`--scenarios`**：显式负载场景（6 例目录见 §17.2，`--help` epilog 列出）。
  给出时替换指标推导的默认集，并**自动补齐 M4/M6 依赖窗口**（M4 → m3-baseline，
  M6 → m3-baseline + m3-flood-uniform），保证探针有证据窗口；未知/空值报错。
- **`--probes`**：显式探针选择（14 名注册表，§17.4）；缺省跑全部已配置探针。
- `--resume`：同 out-dir 中断续跑（语义见 §17.3）。
- `_resolve_profile` 对 instance profile dict 递归展开 `${ENV:-default}` 占位符
  （instance profile 是 JSON，不经 `load_profile`，见 §6/`profile.expand_env_in`），
  再把 tenant_config/preflight_config/fault_plan 相对路径解析为绝对。
- 输出：out_dir/summary.json（观测报告 JSON）+ report.html（自包含 HTML）+
  suite.json + execution-manifest.json（含 `load_scenarios` / `probe_selection`）。
- 输出锁：`.observation.lock`，Windows `msvcrt.locking(LK_NBLCK)` / POSIX
  `fcntl.flock`，句柄关闭即释放；已锁时报 `already locked`；竞争方绝不覆盖
  既有输出。
- `--env-file` 支持 `export KEY=VALUE` / `KEY=VALUE` 行，密钥只进子进程环境，
  绝不写入报告。


### 17.6 观测模式与降级运行

六项指标观测（M1 容量 / M2 公平性 / M3 洪泛 / M4 故障隔离 / M5 崩溃恢复 /
M6 分层可观测）即 `targets/echomem/observation_run.py` 的全部职责
（quick/full/m6 由 `--quick` / `--metrics` 参数表达，无 shell 包装）；
正式验收路径已并入同一入口，`strict` 由 profile 的 `six_metrics_observation`
门控。

**两级证据门**：`readiness.check_readiness(profile, *, strict=True)` 把检查
分为硬门与可选证据门：

- **硬门**（`target-url`、`ready`）：黑盒运行前提，失败 fail-fast 阻断；
- **可选证据门**（`/metrics`、`resource-container`、`fault_isolation`、
  `tenant_observability`）：`strict=True` 任一失败整体 BLOCKED；`strict=False`
  （观测模式默认）失败只记录进 `readiness["degraded"]`，对应指标诚实降级：

| 缺失证据 | 观测落点 |
|---|---|
| `/metrics` 不可达 | M1 资源时序缺失、内存泄漏诊断跳过 |
| 无容器（host-default） | M1 资源口径记 0/None；结构化日志窗口跳过，阶段证据仅 `/metrics` histogram |
| fault 控制面 404/无 token | 跳过 24 例采样矩阵，记 INCONCLUSIVE 命令，M4 BLOCKED |
| tenant-observability 面 404/无 token | 不启动采样线程，M6 BLOCKED |
| 无容器且无 pid/restart_command | 不要求 `allow_container_restart`，恢复探针早退 INCONCLUSIVE，M5 BLOCKED |

降级只把状态推向 INCONCLUSIVE/PARTIAL/BLOCKED，绝不把缺失证据推断成
PASS/MEASURED；`readiness["degraded"]` 与各探针 INCONCLUSIVE 命令保留在
suite.json / execution-manifest.json 供审计。恢复探针
（commit_recovery / disconnect_recovery）的杀进程操作仅在
`allow_container_restart=true` 且 M5/M6 选中或显式 `--probes` 选择时才执行，
其余情况以 INCONCLUSIVE 早退。


## 18. 内存泄漏诊断（通用 `performance/memory_leak.py`）

压测完成后**自动**诊断被测服务的内存泄漏，不绑定任何 target：任何被测系统
只要在 case 目录落盘了 monitor 格式的 `metrics_samples.csv`（
`performance.monitor.write_metrics_csv`）且服务端暴露 resident memory 指标
（metric 名以 `_resident_memory_bytes` 结尾），即可被诊断。

### 18.1 目标

- 从磁盘产物重建 RSS 时间序列并判定泄漏趋势，作为所有压测报告的通用能力。
- 判定必须区分「真泄漏」与「索引/数据规模增长」：用斜率阈值 + 最小观测窗口
  双重约束，短窗口（启动预热/GC 主导）不判泄漏。
- 全程只读磁盘产物，不依赖运行中的服务，压测进行中即可安全执行。

### 18.2 接口

| 函数 | 输入 | 输出 |
|---|---|---|
| `extract_rss_series(csv_path, metric_suffix=..., bucket_s=30)` | metrics_samples.csv 路径 | `(原始点, 30s 分桶均值点)` 或 None（无指标） |
| `rss_trend_mb_per_min(series)` | `(ts, bytes)` 序列（≥4 点） | `{slope_mb_per_min, r2, samples}` |
| `compute_resources(case_dir)` | case 目录 | `{rss_trend, window_s, rss_baseline_mb, rss_peak_mb}` 或 None |
| `evaluate_memory_leak(resources)` | resources dict | verdict dict（PASS/FAIL/INCONCLUSIVE + measurements） |
| `diagnose_case(case_dir)` | case 目录 | per-case verdict dict 或 None |
| `diagnose_runs(runs)` | `[{output_dir, ...}]` | `{verdict, reason, per_case}` 聚合 |

### 18.3 行为约束与边界

- **斜率阈值**：`RSS_LEAK_SLOPE_MB_PER_MIN = 5.0`（MB/min，约 300MB/小时）。
  slope ≥ 阈值 → FAIL；< 阈值 → PASS。
- **最小观测窗口**：`MIN_LEAK_WINDOW_S = 600`。`window_s < 600` 一律
  INCONCLUSIVE（短窗口斜率受预热/GC 主导），不判泄漏，避免短场景误报。
- **降采样**：回归前按 30s 分桶取均值，平滑瞬时波动；样本 < 4 判 INCONCLUSIVE。
- **数据来源**：只认 metric 名以 `_resident_memory_bytes` 结尾的序列；文件缺失
  或指标不存在 → 无诊断（diagnose_case 返回 None，聚合时跳过）。
- **聚合**：任一窗口足够的 case FAIL → 整体 FAIL；有 INCONCLUSIVE 无 FAIL →
  INCONCLUSIVE；全部 PASS → PASS；无任何可判 case → INCONCLUSIVE。
- **接入点**：`suite._finalize_suite` 收尾时 `manifest["memory_leak"] =
  diagnose_runs(runs)`——所有走该收尾的 target（echomem 观测套件经通用
  `suite.run_suite`、general）自动获得；判定随 suite.json 落盘，报告是否渲染
  由各 target 决定（echomem 观测报告当前不渲染该节）。
- **单一实现**：内存泄漏判定只存在于 `memory_leak.py`（`evaluate_memory_leak`），
  无第二份判定逻辑。

### 18.4 测试映射（`performance/tests/test_memory_leak.py`）

- 斜率正/负/零与样本不足；分桶提取只取 resident 指标；PASS/FAIL/短窗口
  INCONCLUSIVE 三分支；`diagnose_runs` 聚合 FAIL 与无数据 INCONCLUSIVE。
